# Plan: controllers push to the gateway

Decision (2026-11-04): the PTS-2 controllers **push** their uploads to our server, over HTTPS, to a name on the
client's domain (proposed `gateway.ranzstation.com`). Pull stays only as a fallback and as a way to fetch history.

Why push: the controller stores up to 100,000 tank records while the network is down and uploads them when it is back;
no VPN or tunnel into each station's network is needed; one server address per controller.

What is **not** known yet (nothing below invents it): the jsonPTS packet format, what reply the controller expects,
what it does when the reply is missing or wrong, which authentication it uses, which TLS versions and certificate types
it accepts. Phase 1 exists to find these out from real traffic, before any parser is written.

## Phase 1: learn the push format

The gateway already has a capture route: `/pts/<station-secret>` stores every request exactly as received (method,
path, headers, raw bytes) and answers with a configurable reply (`CAPTURE_REPLY_STATUS`, `CAPTURE_REPLY_BODY`, default
`200 {"ok":true}`). Three sources, used together:

1. **Logs of the server that receives the uploads today** (`pts.ranzstation.com`, 45.93.138.224, owner unknown). One
   day of the access log and of whatever the application logs gives the path, the request and the reply. Ask the owner
   for a sample with the secrets removed.
2. **Technotrade's jsonPTS specification** (from the client or `mail@technotrade.ua`).
3. **Capture from a test controller** pointed at our capture route. Only a controller that can be spared: changing the
   Server tab of a working controller may stop its uploads to the current server. Ask the client whether a controller
   accepts more than one destination before touching a live one.

**TLS check, as early as possible.** Embedded controllers often support only older TLS settings. Caddy gets its
certificate from Let's Encrypt (an ECDSA certificate by default). Before building anything else, make one real
controller connect to `https://<name>/pts/<secret>` and look at both sides: the controller's own log, and the capture
table. If it cannot complete the handshake, the options are an RSA certificate and different cipher settings in the
Caddyfile; plain HTTP is not an option, because the station secret travels in it.

## Phase 2: parser and reply

Build on the captured samples, with the raw upload stored first and always:

- **Store, then answer.** The reply that tells the controller "received" is sent only after the raw upload is committed
  to the database. The existing capture route already works that way; keep it.
- **Parse into readings** with the same identity rules as the importer: a reading is identified by station, tank and
  device time; a record sent twice is stored once; old and out-of-order records are accepted (backlog).
- **Clock faults:** time 00:00:00 or the year 2000 becomes `clock_invalid` (kept, never chained), as in the importer.
  Time zone comes from the station's `utc_offset_minutes`.
- **A packet we cannot parse:** keep the raw upload, count it, alert; do not drop it. Whether to answer such an upload
  with success or failure depends on what the controller does with a failure (Phase 1 table): if it keeps resending the
  same record for ever and blocks newer ones, answer success and reprocess later.
- **Reprocess tool:** `scripts/reprocess-uploads` reads stored raw uploads again with a newer parser (needed the first
  time a parsing rule changes).
- **Controller simulator:** extend `scripts/sim` so it pushes in the captured format, including backlogs, duplicates,
  out-of-order records, a wrong secret, a dropped connection mid-upload. The end-to-end test runs it against the real
  app and the strict MoEnergy rule checker already in the repository.
- **The tests come from real captures:** the captured bodies (secrets removed) become fixtures.

Exit: the simulator and the real captures both go through the app, the ledger and the strict checker with no rule
violated.

## Phase 3: pilot on one controller

Choose the station with calibration charts (AL HMAIDAN has all five). Then:

1. Load the station with `send_from` set to the go-live time, so no stored history is sent to MoEnergy.
2. Point the controller's Server tab at the gateway, or, if it accepts two destinations, add ours next to the current one.
3. Watch for a week: `GET /v1/stations/{code}/status`, the health check, and a comparison of our readings with a
   `TANKMSR.CSV` pulled from the same controller (`npm run replay:tankmsr`).
4. Run the client's calls against Preproduction with the client's key: first reading of a tank, a refill (negative
   consumed), a batch with a bad item. These settle `NEGATIVE_CONSUMED_POLICY` and the first-reading rule
   (`docs/PREPRODUCTION_PROBES.md`).

Exit: a week without a held tank we cannot explain, no silent-station alarm that was not real, and a Preproduction
answer for each probe.

## Phase 4: the other stations

For each station, in this order, using `docs/ONBOARDING_STATION.md`: codes and tank specs from the client; calibration
chart per tank; one row per tank in the loader file; the upload secret given to the technician; the controller's Server
tab set; the first upload checked in the capture table and in `/status`; `send_from` at the go-live time. One station
per day at first.

## Risks

| Risk | What we do |
| --- | --- |
| The controller cannot complete a TLS handshake with our server | test one real controller early; RSA certificate and cipher settings |
| The reply we send makes the controller discard or repeat records | learn the semantics from real traffic before choosing the reply; keep raw uploads |
| Several controllers share one mobile address, so the rate limit counts them together | the limit is generous (120 a minute per address); raise it if a station is refused |
| A station secret leaks (in the controller's own configuration, in a log) | secrets are stored hashed; rotate by creating a new one and changing the Server tab; Caddy's log hides the path secret |
| Stored history floods MoEnergy when a controller starts uploading | `send_from` at go-live, set per tank |
| No calibration chart: no litres: no readings | the station is not sent until its charts are loaded; `status` shows it |
| A controller's clock is wrong | `clock_invalid`; the health check shows stations whose readings are set aside |
