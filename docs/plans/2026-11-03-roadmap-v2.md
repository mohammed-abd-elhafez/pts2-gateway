# Roadmap v2 (after the first real controller data)

Replaces the "what is next" parts of the earlier plans. Plans 1 to 3 (foundation, client API, per-station links) are built
and reviewed; this is the order of everything else. Evidence for every change below: `docs/REAL_DATA_FINDINGS.md`.

## What changed since the first plans

| Assumption | What the data showed | Effect |
| --- | --- | --- |
| One reading per tank per minute (3.2 readings/s at 38 stations) | about 100 to 120 records per station per day (0.05 to 0.08/s) | storage about 1 to 2 GB a year at 38 stations, under 10 GB at 182. No partitioning, no physical backups, a small server. The replay (burst) tests stay as the worst case |
| Capture 24 to 48 h, then write the parser | `SERVER.LOG` holds no jsonPTS exchange; the controller could not resolve the server name in September; the name now points at a server we do not know | still capture first, but on a name we control, after checking the controller's DNS and internet |
| `TANKDLV.CSV` gives the refills | it recorded 6 deliveries and none since 2026-09-05 | refills are inferred from volume rises: a negative `consumed_quantity` every 3 to 4 days per station. Preproduction probe 3 is the first blocker |
| `(tank, device_time)` is a safe key | 15 % of rows are stamped `00:00:00`, 40 same-second pairs differ | rule `clock_invalid` before any importer or parser |
| Litre volumes exist | only from 2026-09-05, and trusted from 2026-10-04 | importers start at a configurable date, default 2026-10-04 |

## Phase 1: prove the ledger on realistic and real data (code, now)

1. **Simulator** (`scripts/sim/`): a seeded generator calibrated to the numbers in the findings, with the real charts; sinks to
   TANKMSR-format CSV and to the database; a runner that plays the client against a MoEnergy fake and checks invariants
   (chain whole, quantity conserved, no `00:00:00` row sent, injected faults all accounted for, replay is idempotent).
2. **CSV importer** with the quality rules (local time to UTC, skip rows without volume, `clock_invalid`, same-second
   duplicates, start date), then the real `TANKMSR.CSV` through the ledger with a report: sent, set aside (by rule), held.

Exit: both run green in the test suite; the real-file report is read and its set-aside counts are explained.

## Phase 2: operate it (code)

1. Registration: a command to add tanks (probe number, product, capacity, total height) and to store MoEnergy codes;
   `GET /v1/stations/pending` (bodies for the client to register stations and tanks) and an intake for the generated codes.
2. Read-only status for the client: station and tank state (held and why, last reading, unsent count, set-aside counts).
3. Operator actions: requeue set-aside readings, release a hold, resync to the last accepted remaining.
4. An OpenAPI file next to `API.md`.

## Phase 3: the controller channel (after capture)

jsonPTS parser and the reply, a `/jsonPTS` route (or the URI set to `/pts/<secret>`), idempotent `raw_uploads` to `readings`,
signature check if the controller signs, time rules. One controller in a pilot with only tank measurements, in-tank
deliveries and status switched on. Fallback if pushing does not work: an agent on the station PC that polls with the verified
pull request (no history, so a gap is a gap).

## Phase 4: run it

Silent-station alert, small retention job (raw uploads 90 days), backups with a tested restore, `docs/DEPLOY.md`, the pilot,
then 4 stations a month.

## Phase 5: harden

Database role without superuser rights, secret rotation, image digests, rate limits tuned from real traffic.
